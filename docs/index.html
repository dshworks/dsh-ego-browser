ego lite is one browser a human and an agent share — the agent works in its own Space with your real logins, your tabs stay yours. This plugin brings it into dsh and adds the half ego’s own README still lists as coming soon: a store the agent writes. The second time it scrapes that dashboard, it calls a tool it wrote last week instead of rediscovering the page.

$ dsh plugin --profile web add -w @dshworks/dsh-ego-browser
60-second start source npm

The loop

Four tools in the order that matters. Everything else on this page exists to keep step 3 honest.

01

ego_recall

Notes and tool signatures for a hostname, read off disk. No browser, no page load, no tokens spent rediscovering last month.

02

ego_run

One script for the whole browser task — the design ego’s own benchmark is built on. Pass a URL and it prepends what is already known.

03

ego_learn

Promote the step that worked into a real site tool, in ego’s format — and refuse the ones that will not survive to tomorrow.

04

ego_site_run

Call a stored tool by name next session, and count the call. Instead of rediscovering the page.

Anything learned here loads in the stock ego-browser skill outside dsh, and in any other agent pointed at the same workspace. There is no private format and nothing to migrate out of.

The gate that makes the memory worth keeping

The script that just worked is full of @21s, because that is how the agent found the element five seconds ago. Snapshot refs are rebuilt on every snapshotText() call and mean nothing on the next run, so storing that script verbatim stores nothing. ego_learn refuses it:

this is not storable yet:
  - code contains a snapshot ref (@21 / ref=21). Those are rebuilt on every
    snapshotText() call and mean nothing on the next run — re-express the step
    with a stable locator (a CSS selector, or the loc=... value from the
    snapshot) before promoting it.

This is the whole difference between a memory and a pile of dead selectors. The rule is ego’s own — its validator rejects the same pattern — and enforcing it at write time is what turns “it worked once” into “it works again”. A refused promotion leaves the store exactly as it was.

Get started

Needs ego lite installed and onboarded on the machine running dsh (lite.ego.app), so ego-browser is on the PATH.

$ dsh plugin --profile web add -w @dshworks/dsh-ego-browser
$ curl -s localhost:8090/dsh-ego-browser/memory | jq .tools

Restart dsh between the two. Seven names come back, or [] if it did not take. Then ask the agent to run ego_doctor once — it is how the model finds out whether to write cliLog() or console.log() for the ego you happen to have.

The seven tools

toolwhat it does
ego_runRun one script in ego’s runtime. Pass url and it prepends everything already learned about that site. Pass taskSpace and it opens the space first, in the right dialect.
ego_recallNotes and tool signatures for a URL, read off disk.
ego_site_runCall a learned tool by site and name, and count the call.
ego_learnPromote a working step into a real site tool — and refuse it when it will not survive.
ego_forgetRemove a tool or a whole site. A memory that is wrong is worse than none.
ego_handoffHand the browser over with a real Continue / Finish task prompt, and take control back on Continue.
ego_doctorWhich ego, which argv shape, which helper surface, which store, and what is in it.

Seven, not thirty. Granular click / fill / scroll verbs are deliberately absent: ego’s own benchmark attributes its speed to one-script-per-task, so thirty small verbs would spend that advantage to look thorough.

Two runtimes, one command name

Worth stating plainly, because it bites anyone writing against ego. The argv shape is not stable. The shipped skill documents ego-browser nodejs; the CLI in citrolabs/ego-lite@main takes no argv at all and answers a stray nodejs with its usage banner and exit 2. The community Linux port swallows it as a no-op prefix. One command name, three behaviours.

The helper surface is not stable either. One generation installs flat globals — cliLog, snapshotText, useOrCreateTaskSpace. The other installs Playwright-shaped facades — page, browser, taskSpaces — and drops cliLog for console.log. A script written for one throws ReferenceError on the other, and no amount of documentation fixes it because both documents are true somewhere. Even inside ego’s own repo at HEAD, SKILL.md and references/install.md disagree.

So this plugin does not assume. It asks, once per boot, and hands the answer to the model.

And the output sink can eat your result. When the user takes a task space back, ego marks a hard stop and discards every line the script logged, printing only its own guidance. Any integration that parses a result sentinel out of stdout finds nothing there and reports a parse failure. Here the sentinel’s absence is the signal, and the run comes back classified as a takeover rather than as a missing result.

What is not verified

Every path that needs the live browser: an actual page load, a real task space, a real user takeover. ego lite is a macOS app and this was built in a Linux container. The wire into it is exercised end to end against the real CLI bundle; what is on the far side of that wire is not. Run ego_doctor on a real install and open an issue with its output if anything here disagrees with your machine.

When to skip it

You want to watch the agent browse

This plugin has no viewer, and is not going to grow one. Fisfzy/dsh-ego-browser is a live screencast panel you can click through, with a vendored Linux port so it works without the macOS app. It owns that surface and does it well.

You are not on macOS

ego lite ships for macOS today. Same recommendation.

You do browser work once and never again

The memory is the point. Without repetition this is overhead over the plain ego-browser skill.

You need this in CI, headless

ego lite is a desktop app with a real profile. A Playwright plugin is the right tool.
